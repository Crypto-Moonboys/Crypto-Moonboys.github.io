# Telegram Moonboy media — PR2 transport (NOT live)

Parent issue: #1726. PR1 composer merged as #1728.

## Scope

Adds `workers/moonboys-api/telegram/moonboy-photo-transport.js` as an **unused** opt-in transport. No existing Telegram send sites are changed, no Cloudflare Images binding is provisioned, and no Worker is deployed. This is not a production rollout.

`sendTelegramMoonboyMessage({ token, chatId, text, photo, options, fetchImpl })` accepts a PR1-composed JPEG (`{ bytes: Uint8Array, mimeType:'image/jpeg', width:640, height:640 }`) and sends one multipart `sendPhoto` request with the original message as caption. The multipart boundary is generated by `FormData` rather than manually set.

## Preservation

- Exact chat ID, valid `message_thread_id`, `reply_to_message_id`, `reply_markup`, `disable_notification`, `protect_content`, `allow_sending_without_reply`, `parse_mode` and Telegram text/caption entities.
- For photo sends, text entities become `caption_entities`. For text fallback, caption entities become `entities`.
- Texts longer than **1024 UTF-16 code units** use **one original `sendMessage`**, not a photo; this conservative preflight preserves the entire message and avoids a photo-then-continuation partial delivery. Photo captions are shorter than normal text limits. Full text must fit **4096 UTF-16 code units** or the caller must split before invoking this helper. PR3 should explicitly decide if long messages need a two-message flow.
- JPEG photo inputs must be nonempty, 640×640 and **at most 500,000 bytes**. An invalid image is rejected **before** a photo network request, and text is sent instead.
- A **definitive Telegram rejection** (`ok:false` with 400/403/404/413/422) triggers exactly one text-only fallback; no second photo attempt.
- An ambiguous fetch failure, timeout, 429, 5xx, malformed Telegram response or missing acknowledgement returns `status:'uncertain'`. **Never send a fallback or retry** after uncertain photo delivery. The calling feature must persist an uncertainty/review state as appropriate.
- Successful Telegram acknowledgement returns `telegramMessageId` and (when provided) the photo's reusable `telegramFileId`. PR4 will store/reuse it; this PR does not.
- No outbound network action occurs on invalid bot token, chat ID, thread, parse mode or oversized text.

## Limitations

A syntactically valid JPEG buffer is not decoded by PR2: PR1 is responsible for producing valid bytes, and Telegram remains the authoritative photo decoder. The size and dimension metadata are checked but not cryptographically verified. A response containing an acknowledgement can prove Telegram accepted a message; it cannot prove a user saw it. The conservative long-caption fallback is deliberately text-only until a separately approved continuation protocol exists.
