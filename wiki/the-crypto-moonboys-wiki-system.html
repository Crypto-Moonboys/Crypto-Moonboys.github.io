The Three-Repository Wiki Architecture

A public knowledge world needs ways to find material, recognise names and connect related accounts. The wiki/SAM architecture essays describe that ambition through collectors, intelligence and a static public surface.

Three roles, several kinds of evidence

The historical architecture account describes a frontend repository, a collector named HAY-MUM-IM-BUILDING-AGENTS-OF-CHANGE and sam-v2-intelligence. The division gives each role a different question. Where does material come from? How is it interpreted? What can the visitor actually read? The source’s account of that design is a useful record of intent, without certifying the present deployment of each separate repository.

Those roles can be understood independently of any particular software. A collector finds candidate material. An editorial process decides how it relates to existing knowledge. A publisher makes an approved result accessible. Keeping the stages distinguishable helps prevent an interesting discovery from becoming a public assertion before its source has been examined.

A graph is a route through the work

The graph connects subjects so a reader can move from a character to a faction, from a faction to an event, and from an event to the account that describes it. A relationship is useful when it supplies a reason to continue reading. A large number of links alone cannot explain whether two records agree or why the connection matters.

The current site maintains local discovery data for search, entities and graph views. The editorial dashboard reads its own local metadata. These public surfaces provide different views of the same published material. Their consistency depends on generating them from the actual page set, rather than treating a visual node as proof that a full article exists.

A bible is not automatically a verdict

Structured entity summaries can make names and recurring facts easier to retrieve. Some of the repository’s JSON bibles are historical migration records; selected entries also carry an explicit current-canon override. A confident label in an old record should therefore be read with its date, provenance and current authority.

The fictional Agent SAM is a different subject from SAM-labelled publishing software. Samuel HyroSAM Blake has a life inside the household stories. The website’s tools organise documents and interfaces. SPARKY and SWARMSY have another product context again. The shared language of memory connects them imaginatively without making them one running intelligence or one person.

The page remains the public promise

A visitor needs a working destination, a useful title and enough context to understand what they have found. Canonical URLs, source attribution, categories and descriptions are part of that promise. They help an article survive being encountered through search, a graph or a link passed between people.

The architecture becomes valuable through these ordinary outcomes: the story can be read, the source can be followed and a correction can reach the places that display the claim. Automation can assist that work. Approval, ownership and truth still need their own evidence. The public record grows strongest when its tools make those responsibilities visible.

Full Deep Breakdown of the 3-Repo Architecture

The Crypto Moonboys Wiki is not just a website. It is a structured, living knowledge machine built to grow, organize, verify, and publish a deepening universe of lore without collapsing into chaos.

This system is built across 3 connected repositories, each with a different job, a different level of authority, and a different purpose in the overall stack.

At the center of it all is SAM V2 — the main brain.

Beneath that sits SAM 1 / SAM WIK WIKI — the web-crawling field agent.

At the front is the public wiki repo — the visible world people actually explore.

This separation matters because it allows the project to scale hard without breaking canon, breaking design, or turning the wiki into a bloated mess.

1) THE 3 REPOS AT A GLANCE

Repo 1 — Public Frontend / Display Layer

Crypto-Moonboys/Crypto-Moonboys.github.io

This is the public-facing wiki.

It exists to display the Crypto Moonboys universe, not to think.

Its job is to present pages, categories, homepage sections, article pages, bible content, and supporting static data in a clean way through GitHub Pages.

This repo is the face.

It contains things like:

homepage structure

article pages

category pages

wiki pages

static JSON-fed frontend logic

JavaScript loaders for stats and bible content

/wiki/bibles/ content

frontend hooks that allow lore blocks to render on chosen pages

This repo should stay lean, predictable, and stable.

It is not supposed to become an AI lab, a crawler, or a live decision engine.

It is the display layer.

Repo 2 — SAM 1 / SAM WIK WIKI / Field Hunter Layer

HODLKONG64/HAY-MUM-IM-BUILDING-AGENTS-OF-CHANGE

This is the original operational SAM cycle repo.

This layer is the crawler, orchestrator, and publisher.

This is the system that goes out into the field and hunts for relevant Crypto Moonboys universe material across locked official sources and approved discovery flows.

This repo does the dirty work:

source crawling

discovery

extraction

validation

workflow execution

publishing preparation

controlled output generation

This is SAM WIK WIKI.

In lore terms, this is the roaming hunter.

He crawls the web looking for the Crypto Moonboys, gathering pieces, noticing signals, chasing mentions, and building raw understanding. He thinks he is just a seeker, but in deeper story terms he is really acting like NULL THE PROPHET’s companion and spy — collecting fragments from the edges of the system and feeding them back into the higher intelligence.

He is not the final authority.

He is the collector, scout, and mover.

This repo is responsible for:

running the master cycle

coordinating what gets processed

preparing outputs

publishing safe, structured updates toward the frontend layer

keeping changes operational and controlled

So this repo is the field agent + publisher pipeline.

Repo 3 — SAM V2 / Intelligence Brain / Backend Layer

HODLKONG64/sam-v2-intelligence

This is the real brain.

SAM V2 is the main intelligence layer of the whole system.

It is where structure, reasoning, ranking, scoring, memory strategy, planning, and deeper knowledge architecture live.

If Repo 2 is the hunter, Repo 3 is the mind that decides what the hunt means.

intelligence logic

scoring entities

ranking importance

focus-plan logic

memory structure

leaderboard systems

keyword-bank logic

bible generation pathways

backend/API capability

dashboard/intelligence-layer functions

It is the repo that gives the whole machine direction.

SAM V2 is not just a tool.

It is the system that turns raw accumulation into organized intelligence.

That means:

deciding what matters more

deciding what is weak and needs expanding

deciding which entities deserve priority

deciding how deep a topic has become

deciding how memory should evolve

deciding how future lore infrastructure scales

So in the cleanest terms:

Repo 2 gathers

Repo 3 thinks

Repo 1 displays

That is the system.

2) WHY THE SYSTEM IS SPLIT INTO 3 REPOS

This split is not over-engineering.

It is there because a project like this can get huge very fast.

The Crypto Moonboys universe is not a tiny wiki.

It is a deep, expanding, multi-layered lore system with characters, factions, mechanics, timelines, symbols, hidden meanings, ecosystem links, and future content that can grow daily or even hourly.

If everything lived in one repo, the result would be:

tangled logic

fragile publishing

broken pages

dirty automation

hard-to-debug workflows

design drift

impossible scaling

So the 3-repo split protects the system from itself.

The split creates discipline:

one repo for public output

one repo for operational crawling/publishing

one repo for intelligence and long-term structure

That means each part can evolve without wrecking the others.

3) THE ROLE OF SAM V2 AS THE TRUE BRAIN

This matters most.

SAM V2 is the main brain.

Not the homepage.

Not the crawler.

Not the hooks.

SAM V2 is where the higher-order intelligence belongs.

Its purpose is not just to store information.

Its purpose is to understand the shape of the universe being built.

That includes:

what entities exist

how important they are

how complete they are

how often they are referenced

how they connect to other entities

which areas are underdeveloped

which topics deserve bible treatment

which clusters are emerging

which knowledge paths should be expanded next

SAM V2 is the long-game layer.

It is the layer that should ultimately govern:

memory health

entity confidence

ranking systems

depth progression

relationship logic

future bible generation

controlled expansion of the wiki universe

In simple terms:

SAM 1 sees.

SAM V2 knows what it means.

4) THE ROLE OF SAM 1 / SAM WIK WIKI

SAM 1 is still crucial.

Even though SAM V2 is the main brain, SAM 1 remains the active crawler and field scout.

This repo is the boots-on-the-ground intelligence gatherer.

Its purpose is not to become the deepest thinker.

Its purpose is to:

move through official source terrain

gather what is new

detect what changed

collect material

package it for structured processing

feed the machine

It is the hunting arm of the operation.

That means its value is in:

persistence

repeatable cycle logic

source discipline

output preparation

controlled publishing pathways

This is why SAM 1 still matters even if SAM V2 is the true brain.

Without SAM 1, the system has less field motion.

Without SAM V2, the system has less meaning.

You need both.

5) THE PUBLIC WIKI REPO IS NOT THE BRAIN

This needs to stay clear.

The frontend repo is not where the intelligence should live.

It should not become:

the crawler

the validator

the memory engine

the scoring layer

the live reasoning system

It is the place where the final result is shown.

Its power comes from:

stability

readability

visual consistency

lightweight static delivery

GitHub Pages survivability

low dependency risk

The public site must survive even if backend ambitions change later.

That is why the current model is strong:

generate structured files

commit/publish them

serve them statically

let frontend JS read them

That keeps the site alive even without depending on a fragile always-on hosted backend.

6) HOW THE 3 LAYERS WORK TOGETHER

The simplest breakdown is this:

Layer A — Discovery and Movement

SAM 1 hunts, crawls, discovers, extracts, and prepares.

Layer B — Intelligence and Meaning

SAM V2 scores, ranks, structures, remembers, prioritizes, and plans.

Layer C — Presentation and Experience

The public wiki displays the output, pages, bible injections, stats, categories, and visible lore surface.

That creates a clean directional flow:

Source world → SAM 1 → SAM V2 → public wiki

Or in looser story language:

the signal is found → interpreted → revealed

7) WHY THIS SYSTEM CAN SCALE

This architecture is built for expansion.

As lore deepens, the project does not need to collapse under its own weight because the jobs are divided properly.

The frontend can scale because:

it is mainly static

it is stable

it does not need to think on every request

SAM 1 can scale because:

it focuses on collecting and operational movement

it does not have to carry the full intelligence burden alone

SAM V2 can scale because:

it is the dedicated intelligence layer

it can evolve ranking, memory, and bible systems without breaking the public site

This matters because the Crypto Moonboys universe is designed to get deeper over time, not flatter.

You do not need a website that just lists pages.

You need an architecture that can absorb expanding mythology.

This 3-repo system is what makes that possible.

8) THE BIBLE SYSTEM INSIDE THE ARCHITECTURE

The bible system is one of the most important bridges between intelligence and display.

The public site now has the ability, on selected pages, to carry:

entity slug hooks

bible content insertion points

That means the frontend is being prepared to render deeper entity-specific content in a structured way.

This is important because it allows the system to move beyond flat article pages and toward:

living entity dossiers

structured lore blocks

deeper expandable character/faction/topic intelligence

richer on-page context without rewriting whole page templates

In this structure:

SAM 1 helps gather

SAM V2 helps define and shape

the frontend renders the result

That is how bible content becomes part of the larger ecosystem instead of a random bolt-on feature.

9) THE CURRENT DESIGN PHILOSOPHY

The strongest part of the current setup is that it favors survival and control over hype.

Instead of making the site depend entirely on a live backend, the current direction keeps the frontend durable:

static files

static JSON

repo-served assets

GitHub Pages-friendly outputs

That means the public layer can keep breathing even if live services are paused, moved, upgraded, or rebuilt later.

This is the right way to build a universe that is supposed to outlive individual experiments.

The intelligence layer can grow.

The crawler layer can evolve.

The public site stays standing.

That is how a real long-term lore machine should be built.
